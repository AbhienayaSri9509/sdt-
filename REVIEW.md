# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33–37) | Replaced `punch_in` hour/minute without considering time zones (comparing naive or mixed datetimes). Also calculated `minutes > 10` using truncated integer minutes instead of checking if punch-in is *strictly more than* 10:00 (600 seconds) after `shift_start` (R2). When late, it did not take the floor of elapsed minutes correctly across overnight shifts or dates. | A punch-in at 09:40:00 for a 09:30 shift start evaluated to > 10 min late in certain environments or failed to calculate exact elapsed minutes (e.g. 09:40:01 should yield 10 min late; 09:40:00 should yield 0). | Fixed timezone normalization to IST, parsed calendar shift start combined with attendance date, checked `diff_sec > 600`, and floored whole minutes `int(diff_sec // 60)` elapsed from `shift_start`. |
| 2 | `compute_work_hours` (lines 40–41) | Used standard Python float `round(..., 2)` which uses banker's rounding (round half to even) rather than round half-up (R4, R8). | For elapsed durations ending at .005 hours (e.g. 4.495 hours), standard round rounds to 4.49 instead of 4.50, causing misclassification of half-day status. | Used `decimal.Decimal` with `ROUND_HALF_UP` quantized to `0.01` per R4 and R8. |
| 3 | `compute_overtime` (lines 44–47) | Did not enforce the minimum 30-minute threshold required by rule R3 (`diff_min >= 30`); any positive minutes (e.g., 5 min) were recorded as overtime. Also did not account for overnight shifts (`shift_end <= shift_start`) where shift end falls on the next calendar day. | For a punch-out at 18:35 (shift end 18:30), returned 5 minutes overtime instead of 0 (per sample doc 1). For overnight shifts (22:00–06:00), punch-out at 06:40 on day+1 computed negative or wrong day overtime. | Implemented R3 checking `is_overnight = shift_end <= shift_start` adding 1 day to shift end date when overnight, and only returning overtime when elapsed minutes `>= 30`, otherwise returning 0. |
| 4 | `EmployeeIn` / `POST /employees` (lines 53–61, 78–85) | Model lacked required field validators (e.g., `emp_code` regex pattern `^EMP\d{4,6}$`, email pattern, min/max lengths, `joined_on` date format). Did not check that `shift_start` must differ from `shift_end`. | Invalid inputs such as `emp_code: "123"` or identical shift start and end ("09:00", "09:00") returned 201 instead of 422. | Added Pydantic field constraints, regex pattern validators, and checked `shift_start != shift_end` returning 422 on validation errors. |
| 5 | `POST /employees` (lines 78–85) | Relied on a non-atomic `db.employees.find_one(...)` check before inserting. In a race condition between concurrent duplicate requests, both could pass the check and create duplicate records. In addition, no unique index was created at startup. | Simultaneous concurrent `POST /employees` requests with identical `emp_code` resulted in duplicate records or race conditions. | Created a unique index on `emp_code` at startup and handled `DuplicateKeyError` to return 409 Conflict. |
| 6 | `POST /employees` (lines 82, 84–85) | `created_at` was set as a local naive datetime (`datetime.now()`) instead of UTC BSON date, and was returned as an internal datetime object or string instead of epoch milliseconds (integer) required by the contract. | The response returned `created_at` formatted as ISO string / datetime rather than integer epoch milliseconds, failing schema validation. | Stored UTC BSON datetime truncated to seconds in MongoDB and serialized to integer epoch milliseconds in API responses. |
| 7 | `GET /employees` (lines 88–96) | Incorrect pagination logic: `skip = page * page_size` skipped the first page entirely (page 1 skipped 20 documents). `total` was computed via `db.employees.count_documents({})` which ignored the `department` query filter. `page_size` was not capped at 100. | Querying page 1 returned items starting from index 20 (page 2). When filtering by department, `total` returned the total collection count instead of the filtered count. Querying `page_size=500` allowed unrestricted page sizes. | Corrected `skip = (page - 1) * page_size`, passed filter `q` to `count_documents(q)`, added `page_size: Query(le=100)`, and sorted by `emp_code` ascending. |
| 8 | `PunchInIn` / `POST /attendance/punch-in` (lines 63–67, 99–122) | `punched_at` did not validate epoch milliseconds range (contract requires integer >= 100000000000 and <= 4102444800000); float/string/seconds timestamps were accepted or caused unexpected conversion. | 9 | `POST /attendance/punch-in` (lines 101–105) | Did not check if the employee exists in the `employees` collection (contract requires 404 for unknown employee). | Punching in with an unseeded `emp_code` (e.g. `EMP9999`) caused a `KeyError: 'shift_start'` resulting in an unhandled 500 error instead of 404. | Looked up employee first and raised `HTTPException(404, "Employee not found")`. |
| 10 | `POST /attendance/punch-in` (lines 102–104) | Attendance date calculation `d = ts.date().isoformat()` used local server time instead of IST (UTC+05:30), and failed to implement R1 overnight shift rule (a punch-in before shift end belongs to the previous day's shift). | An overnight worker punching in at 01:10 IST on July 7th had their record assigned to 2026-07-07 instead of 2026-07-06. | Implemented `compute_attendance_date` with IST conversion and overnight shift rule (R1). |
| 11 | `POST /attendance/punch-in` (lines 104–105, 118) | Check-then-insert race condition: `db.attendance_logs.find_one(...)` followed by `insert_one`. Under concurrent punch-ins, both requests could insert, violating the business rule. | Parallel punch-in requests for the same employee and date could both succeed or corrupt collection state. | Added unique compound index `[("emp_code", 1), ("date", 1)]` at startup and caught `DuplicateKeyError` to reliably return 409. |
| 12 | `POST /attendance/punch-in` (lines 119–120) | Included an artificial `"id": str(res.inserted_id)` field in the response body. The OpenAPI contract explicitly forbids returning MongoDB ObjectId or id field; records are addressed by `(emp_code, date)`. | Response contained an illegal `"id"` field and `punch_in` was returned as a Python datetime rather than integer epoch milliseconds. | Stripped `_id` and `id`, formatted response according to `AttendanceRecord` schema with integer epoch milliseconds. |
| 13 | `GET /attendance` (lines 124–150) | Loaded the entire filtered collection into memory with `list(db.attendance_logs.find(q))` and sorted in Python `docs.sort(...)`. This violates the contract specification to stay fast on ~100k documents without loading into memory. Also lacked compound sorting (`date` descending, then `emp_code` ascending). | Querying on a collection with 100,000 records would cause high memory pressure and slow response times. | Used database-level streaming cursor with `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` backed by index `("date", -1), ("emp_code", 1)`. |
| 14 | `GET /attendance` (lines 137–141) | Did not validate that `date_from <= date_to`; if `date_from > date_to`, returned an empty page instead of raising 422 Unprocessable Entity as required by the contract. | Querying `/attendance?date_from=2026-07-10&date_to=2026-07-01` returned 200 with empty list instead of 422. | Added validation checking `date_from > date_to` and raised `HTTPException(422)`. |
| 15 | `GET /attendance` (lines 148–150) | Mutated documents and returned `d["id"] = str(d.pop("_id"))`, exposing MongoDB's internal `_id` as `id`. In addition, `punch_in` and `punch_out` were returned as BSON datetimes rather than epoch milliseconds. | Client received unexpected `id` property and datetime strings/objects, causing schema validation failures. | Sanitized output via `serialize_attendance_doc`, returning epoch milliseconds and omitting `_id` and `id`. |
| 16 | `GET /health` (lines 72–74) | Dummy endpoint returning static `{"status": "ok"}` without checking database connectivity. Contract requires checking MongoDB readiness (e.g. ping command) and returning 503 if unavailable. | If MongoDB was stopped or unreachable, `/health` still returned 200 OK. | Executed `client.admin.command("ping")` and returned 503 on failure. |

## Items examined and determined NOT to be defects
* **IST as a fixed offset (+05:30) vs ZoneInfo**: Using `timezone(timedelta(hours=5, minutes=30))` is correct and robust because Indian Standard Time does not observe Daylight Saving Time (DST). A fixed UTC+05:30 offset is reliable, fast, and does not depend on system timezone databases.
* **Separation of calendar dates as strings**: `date` and `joined_on` stored as `"YYYY-MM-DD"` strings in MongoDB. As described in `DATA_MODEL.md`, calendar dates are intentionally plain strings to prevent accidental timezone shifts, while instants are UTC BSON dates.
